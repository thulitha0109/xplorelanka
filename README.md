# Xplore Lanka deployment

Laravel 13 / PHP 8.4 application with PostgreSQL, Redis, PHP-FPM, Vite assets, and S3-compatible media storage. Production and staging run in Docker Compose. **Nginx runs on the host and is configured separately; no Compose deployment starts an Nginx container.**

## Production request flow

`Browser → host Nginx (TLS, xplorelanka.com + www) → 127.0.0.1:9000 (PHP-FPM) → Laravel`

Host Nginx serves files from the checked-out release's `public/` directory, including the commit-matched `public/build` generated by the deploy script. PHP requests go to FastCGI (not HTTP) and execute `/var/www/public/index.php` inside the application image. Uploaded media is stored in an external S3-compatible bucket, never in the web root.

## One-time server setup

1. Provision a Linux server with Docker Engine/Compose v2, Git, Nginx, Certbot, OpenSSL, and `curl`. Allow inbound TCP 80/443; keep PostgreSQL/Redis private. Point both `xplorelanka.com` and `www.xplorelanka.com` DNS records at the server.
2. Clone the production branch to `/srv/xplorelanka`. For staging, use a separate checkout at `/srv/xplorelanka-staging` and the `stag` branch. The paths in the supplied Nginx configs must match the checkout locations. The deployment scripts also support `APP_DIR=/path/to/checkout`.
3. Create the environment file and generated Laravel/database secrets:

   `bash deploy/setup-env.sh production`

   For staging run `bash deploy/setup-env.sh staging` in the staging checkout. Edit the created private file (`.env.production` or `.env.staging`) to provide the S3 credentials, bucket, public URL/CDN, and mail configuration. Use **separate database and object-storage buckets/credentials for staging**. Never commit or bake environment files into images.
4. Create the S3 bucket and least-privilege credentials before deploy. The bucket must permit the intended public-read policy (uploads are marked public) or be fronted by a public CDN. Set `AWS_URL` to that browser-reachable URL. For compatible providers configure `AWS_ENDPOINT`; set `AWS_USE_PATH_STYLE_ENDPOINT=true` where required. Do not set `AWS_URL` to a Docker-only endpoint. Existing locally stored uploads are not automatically moved; migrate them and update stored URLs/paths separately.
5. Install [deploy/nginx/acme-bootstrap.conf](deploy/nginx/acme-bootstrap.conf) manually as the temporary host Nginx site config. Verify the webroots match the checked-out paths, then test/reload Nginx and issue the first certificate with Certbot's webroot mode for `xplorelanka.com` and `www.xplorelanka.com` (add `staging.xplorelanka.com` with its separate webroot if staging is used). Replace the bootstrap config with [deploy/nginx/xplorelanka.com.conf](deploy/nginx/xplorelanka.com.conf), and optionally [deploy/nginx/staging.xplorelanka.com.conf](deploy/nginx/staging.xplorelanka.com.conf). Obtain certificates before enabling the TLS configs because they reference `/etc/letsencrypt/live/...`. The production config redirects HTTP and `www` to HTTPS apex, limits PHP execution to Laravel's front controller, and uses FastCGI to `127.0.0.1:9000`.
6. The staging config targets `127.0.0.1:9001` and `/srv/xplorelanka-staging/public`. Set `APP_URL=https://staging.xplorelanka.com` and use a certificate for that host.

The Nginx server blocks are deliberately **not** installed or managed by Docker or the application deploy scripts. After editing a site file, run `sudo nginx -t` and reload the host Nginx service.

## Deploy

Run from the matching checkout after committing code to the remote branch:

- Production: `bash deploy/prod.sh` (default branch `stag` in this repository; override with `--branch NAME` or `PRODUCTION_BRANCH=NAME`)
- Staging: `bash deploy/staging.sh` (default branch `stag`)
- Select a branch: `bash deploy/prod.sh --branch stag`
- Deploy a known commit: `bash deploy/prod.sh --revision <commit>`
- Seed staging content, only when intentionally needed: `bash deploy/staging.sh --seed`

The scripts check required tools, protected environment-file permissions, S3 credentials, and Compose configuration; take an atomic deployment lock; fetch the requested commit; build a commit-tagged image; publish its built frontend assets to host `public/build`; wait for Postgres/Redis; make and verify a compressed database backup; apply migrations once; rebuild Laravel caches with checked errors; recreate app/worker/scheduler; and check the public `/up` endpoint. Production deploys never run seeders. There is no `--skip-build` path. Failed public health checks restore the previously recorded app image when available, but **do not automatically reverse database migrations**.

Keep migrations backward-compatible (expand/contract) so the prior code image remains compatible during image rollback. Backups are retained locally under `.backups/`; copy them to an off-host backup target and configure retention/restore drills. S3 object versioning/retention is configured at the storage provider, separately from this database backup.

## Local development

For a fresh checkout, install the bind-mounted PHP/JS dependencies (`composer install` and `npm ci`) and create `.env` from `.env.example`, then run `docker compose up -d --build`. The development stack uses [docker/dev/Dockerfile](docker/dev/Dockerfile), runs as the host-matched non-root user, and initializes a public-read MinIO bucket using the already-installed AWS SDK. `.env.example` contains local-only credentials; keep `AWS_ENDPOINT=http://minio:9000`, path-style addressing, and the browser-facing URL aligned with your host ports. The production build uses [docker/prod/Dockerfile](docker/prod/Dockerfile), deterministic `npm ci`, and the Composer lockfile. Do not use development Compose or `dev-build.sh --fresh` against production data.

## Runtime and storage notes

- PHP-FPM is bound only to loopback (`9000` production, `9001` staging); Postgres/Redis have persistent Compose volumes. No container publishes ports 80/443.
- S3 uploads use Laravel's S3 filesystem driver. Storage failures are logged and returned as errors rather than silently falling back to ephemeral local storage.
- The S3 Flysystem adapter and AWS SDK are Composer dependencies. Keep `composer.lock` committed and build from it.
- `.env.production` and `.env.staging` should be mode `600`. Production `APP_DEBUG` is forced off in Compose; staging also defaults off.
- Do not run `db:seed` in production. Staging seeding is explicit and non-destructive migration is always used; never use `migrate:fresh` in deployment.
